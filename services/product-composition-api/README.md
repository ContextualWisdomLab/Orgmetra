# Orgmetra product composition

This service package is the first executable slice of Orgmetra's product-composition boundary tracked by #432. It validates whether configured product routes refer to exact immutable owner API releases before those routes are eligible for a composition generation. Route admission by itself is not buyer or product readiness.

The current contract binds a generation to a deterministic digest of the canonical semantic route projection, rejects route templates whose HTTP authority can select the same concrete request under different owners, binds each logical `service://` upstream to the exact `owner_release.service_id`, and requires exact owner service/release/OpenAPI/artifact coordinates. Because the routed owner APIs in this contract are Orgmetra-owned services, `OwnerApiRelease.release_locator` is restricted to the canonical `ContextualWisdomLab/Orgmetra` GitHub Release namespace; another CWL repository cannot be presented as the release authority for an Orgmetra owner service merely because its tag string and supplied digests match. Configuration identity is minted only after both per-route and cross-route invariants pass: duplicate `route_id` values, overlapping effective method/path authority, and multiple exact release identities for one owner `service_id` fail before `configuration_sha256(...)` returns a digest. Nested route and owner-release invariants are revalidated before route material can be hashed into `config_sha256` or accepted into a `CompositionGeneration`; low-level mutation therefore cannot turn already-invalid nested evidence into a canonical-looking configuration identity and defer the failure until later admission. A single `service_id` must resolve to one exact `OwnerApiRelease` across the entire generation because the observed owner snapshot is keyed by `service_id`; admitting two release identities for the same owner would create a generation that cannot be satisfied by one coherent runtime snapshot. GET and HEAD are one selected-resource authority for this purpose: RFC 9110 defines HEAD as identical to GET except for response content, so two different owners cannot split GET and HEAD for the same overlapping route template. One route may expose both methods together. Complete `.` and `..` URI path segments are rejected before they can become route authority; RFC 3986 removes those dot-segments during reference normalization, so admitting them as distinct route templates would let different routing layers disagree about the selected path. Mutable branches, floating release labels, copied owner schemas, reachability-only checks and digest-only pointers do not qualify as route authority. A canonically constructed generation also retains a process-local construction snapshot of its schema, generation identity and configuration digest. Admission revalidates that snapshot plus the current nested route, owner-release and configuration-digest evidence immediately before use, so low-level mutation cannot rewrite the generation identity or coherently retarget the route graph by changing both route material and `config_sha256` after construction. Construction is serialized and one live process cannot give one `generation_id` two configuration meanings. Multiple live views of the same semantic generation remain valid, and a canonically issued `AdmissionReceipt` leases its source `CompositionGeneration` for as long as that receipt remains live; dropping the caller's generation reference therefore cannot free the lineage while canonical admission evidence still exists. The in-memory binding is released only after the last generation view and canonical receipt are gone. This live-lineage guard is deliberately not durable identity allocation: after those process-local views are released or the process restarts, only a future immutable activation/configuration registry can prove that the generation identifier was never reassigned across process lifetimes. Route ordering is intentionally non-semantic in the configuration digest; admission therefore emits admitted and unavailable route IDs in canonical `route_id` order so the same semantic generation cannot produce different receipt evidence merely because an equivalent route tuple was reordered.

It does **not** authenticate Keyverse tokens, bind identity subjects to People records, authorize HR resources, proxy HTTP traffic, own retry/idempotency/concurrency policy, query bounded-context databases, or make HR/scientific decisions. Those authorities remain with their existing owners. `AdmissionReceipt` is issued only by the canonical in-process `admit_generation(...)` evaluator; direct construction and low-level unissued objects cannot claim `required_routes_admitted`. Canonical issuance retains the exact issued field tuple plus a process-local lease on the source generation; `required_routes_admitted` fails closed if the receipt's generation/config/route fields are changed after issuance, including through low-level `object.__setattr__` mutation, or if that lease no longer matches the receipt identity. The receipt, its generation lease and the generation construction snapshot are process-local structural integrity evidence only. They are not serialized/durable trust artifacts, HR authorization, or buyer-readiness evidence; a later activation boundary must re-evaluate the exact immutable generation and observed released-owner evidence rather than trust reconstructed or mutated receipt-shaped data.

Current scope is deliberately transport-neutral. The package can sit behind a future released shared edge runtime or another approved ingress without changing its contract. Retry/replay safety is never inferred from a composition-local class; when a runtime slice eventually performs replay, permission must come from the exact released owner operation contract under the observed request state.

Production completion still requires released Keyverse consumer evidence, Orgmetra identity ACLs, real downstream owner OpenAPI/behavior releases, an executable HTTP composition host, security and failure/recovery/rollback evidence, deployment provenance, protected exact-head CI, and full buyer-path performance verification.
