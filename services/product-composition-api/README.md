# Orgmetra product composition

This package is the first executable slice of the product-composition boundary tracked by #432. It decides whether configured product routes refer to exact immutable Orgmetra owner API releases before they are eligible for a composition generation. Route admission by itself is not buyer/product readiness.

A generation is bound to a deterministic digest of canonical semantic route material. Each `OwnerApiRelease` retains a process-local construction snapshot of its service/release/OpenAPI/artifact/locator identity, and each `CompositionRoute` retains a process-local snapshot of its route ID, path template, methods, exact owner release, logical upstream, and required/optional status. Route construction revalidates the nested owner snapshot, while configuration hashing revalidates the route snapshot itself. A previously constructed owner or route object therefore cannot be low-level-retargeted to another otherwise-valid semantic coordinate and then presented as fresh configuration evidence; legitimately different release or route semantics require newly constructed value objects. Configuration identity is minted only after per-route and cross-route invariants pass. Owner release evidence must identify the canonical `ContextualWisdomLab/Orgmetra/releases/tag/<version>` coordinate, each `service_id` has one exact release/OpenAPI/artifact identity per generation, and each logical `service://` upstream must name that same owner service. Owner, route, and generation identifiers use canonical 1..64-character lower snake_case with no empty underscore-delimited segments; the mandatory `service://` projection uses the equivalent hyphenated form and therefore has the same representable identity domain. Mutable branches, floating labels, copied schemas, reachability-only checks, and digest-only pointers are not route authority.

## Supported OpenAPI route profile

Protected `docs/API_CONTRACT.md` remains the product contract and declares OpenAPI 3.2.0. OpenAPI Specification 3.2.1 is used here only as the current patch-level interpretation of the same 3.2 feature set; this canary is not a general OpenAPI parser and does not claim support for every path or operation form that OpenAPI 3.2 permits.

The admitted product-route dialect is intentionally narrower while no released owner contract requires a broader surface. A route path starts with `/v<digits>`, uses restricted ASCII literal segments, and uses a whole path segment for each canonical 1..64-character lower-snake-case template expression; repeated or trailing underscores therefore fail closed rather than becoming alternate parameter identities. The admitted method set is exactly `DELETE`, `GET`, `HEAD`, `OPTIONS`, `PATCH`, `POST`, and `PUT`. OpenAPI-valid forms outside that profile—including a template expression mixed with literals in one segment, percent-encoded or other unsupported `pchar` literals, and `TRACE`, `QUERY`, and `additionalOperations` methods—fail closed before configuration identity. Expanding the dialect requires released owner evidence plus explicit conformance tests; it is not inferred merely because a framework can route the form.

Route identity follows three separate layers:

1. **OpenAPI path-key identity.** OpenAPI Specification 3.2.1 §4.8.1 says templated paths with the same hierarchy but different template names are identical and MUST NOT coexist. `/v1/people/{person_record_id}` and `/v1/people/{worker_record_id}` therefore cannot both acquire configuration identity, even when their HTTP methods differ. Distinct methods may share the same exact template string only within one exact owner release in the current Orgmetra profile. OpenAPI's Path Item Object also carries path-level `$ref`, `summary`, `description`, `servers`, and `parameters`; `servers` services all operations on the path and path-item parameters apply to all operations. The current composition canary has no cross-owner Path Item merge or conformance contract, so splitting one exact path across owner releases would make those shared semantics unverifiable.
2. **OpenAPI path matching.** The same section, with §4.8.2.1's examples, gives a concrete non-templated path precedence over its templated counterpart and treats ambiguous templated matching as tooling-dependent. Path selection therefore cannot be made safe merely because two overlapping routes use different HTTP methods: the Path Item is selected before an operation on it is meaningful. The admission model permits different overlapping path strings only for the deterministic concrete-before-template case when both routes belong to the same exact owner release and declare the same method set. Thus one owner may publish `GET /v1/people/current` beside `GET /v1/people/{person_record_id}`. Cross-owner concrete/template overlap, same-owner concrete/template overlap with different method sets, and ambiguous overlap between two templated paths all fail before configuration identity, even when the routes' methods are disjoint.
3. **HTTP operation authority.** Only after Path Item ownership and path matching are deterministic does operation collision matter. Distinct methods may coexist on one exact path only under the same exact `OwnerApiRelease`. For overlapping effective operations, RFC 9110 makes GET and HEAD one selected-resource collision authority while the methods actually declared remain exact contract material.

The one-owner-per-Path-Item rule is an Orgmetra fail-closed product decision, not a claim that OpenAPI itself assigns repository or bounded-context ownership. A future released composition contract may broaden this only if it defines and tests how every path-level field and operation from multiple owner descriptions is combined without ambiguity.

OpenAPI 3.2.1 §4.8.2 also says each template expression MUST NOT appear more than once in one path template, so `/v1/tenants/{record_id}/people/{record_id}` fails before hashing/admission. Complete RFC 3986 `.` and `..` path segments are rejected rather than normalized into another route identity.

The composition contract has no local retry class, idempotency mode, concurrency mode, HR authorization policy, or scientific truth. Those semantics remain with released owner contracts. `AdmissionReceipt` is issued only by the canonical in-process evaluator; its exact fields and source generation are leased in process-local closure state. Receipt validation rechecks the source generation, nested owner/route evidence, and canonical configuration digest, so post-issuance source mutation invalidates stale evidence.

Canonically constructed `OwnerApiRelease`, `CompositionRoute`, and `CompositionGeneration` values retain process-local construction snapshots of the semantic coordinates they are allowed to represent. One live process therefore cannot reinterpret an already-constructed route as a different route/configuration meaning, nor give the same live `generation_id` two configuration meanings while generation views or canonical receipts remain live. These construction snapshots are process-local integrity evidence and are deliberately separate from durable configuration authority.

## Durable generation registry

The #435/#436 successor projects an admitted generation into normalized `GenerationRecordSet` rows and persists those rows through `PostgresGenerationRegistry`. Migration `0018_product_composition_generation_registry.sql` defines append-only generation, owner-release, route, and route-method tables. The generation primary key prevents identity reassignment; composite foreign keys prevent routes or methods from surviving without their generation and owner/route parents. UPDATE, DELETE, and TRUNCATE are all rejected for every registry relation, so the database cannot erase or rewrite accepted configuration history through a destructive table operation. The adapter uses one DB-API connection context for the full insert so partial child persistence rolls back with the generation row.

Registration is idempotent only for exact durable material. `INSERT ... ON CONFLICT DO NOTHING RETURNING generation_id` arbitrates concurrent attempts on the generation key; a losing writer reloads the committed normalized rows and succeeds only when the entire `GenerationRecordSet` is identical. Reload reconstructs fresh canonical `OwnerApiRelease`, `CompositionRoute`, and `CompositionGeneration` values and recomputes `config_sha256`, so a stored digest without complete matching semantic material cannot become authority after restart.

The migration number is deliberately `0018`: open migration-owner lanes already contain `0014`–`0017`, and this branch must not reuse those numbers. The registry tables remain product-composition truth only and contain no tenant/HR/Keyverse/scientific data. `tests/test_product_composition_generation_registry_postgres.sh` exercises atomic write/reassignment/update/delete behavior; the separate truncate contract exists because PostgreSQL row triggers do not protect `TRUNCATE`.

## Durable deployment activation draft

The dependent activation slice now uses ordered migrations `0019` through `0022` on top of the generation registry. `0019_product_composition_activation_registry.sql` defines explicit non-PII `(deployment_id, environment_id)` identity, external evidence/owner-operation records, and an append-only activation-event sequence. `PostgresActivationRegistry` creates and locks the exact deployment row with `FOR UPDATE`, compares the caller's expected previous sequence to durable state, reconstructs the target generation from migration 0018 material, and appends exactly one successor event. Rollback is another event and is allowed only for a generation previously active on the same deployment. `0020_product_composition_activation_authority_enforcement.sql` refuses predecessor NULL-evidence activation history before requiring evidence on current activation events. `0021_product_composition_activation_observation_wall_clock.sql` makes PostgreSQL reject fresh owner-operation observations dated after the database wall clock or already stale at persistence, and refuses upgrade over impossible future-dated predecessor history.

Migration `0022_product_composition_recovery_attestation.sql` adds append-only durable restart re-admission history. Each recovery attestation binds one deployment, the exact current activation sequence and generation, and a content-addressed evidence bundle whose action is `recover` for that same active sequence. PostgreSQL rechecks evidence expiry and exact fresh owner-operation coverage before accepting the attestation. UPDATE, DELETE and TRUNCATE are rejected for recovery attestations as they are for activation history.

`DeploymentIdentity` also retains a process-local construction snapshot. A low-level valid-to-valid rewrite such as `production` to `staging` cannot redirect an already-constructed identity object before database access; a genuinely different deployment coordinate requires a new value object. This is defense in depth only. The durable row key and transaction lock, not the Python object snapshot, are the cross-process serialization authority.

`activation_authorization.py` adds the product-facing external re-admission boundary. `ActivationAdmissionEvidence` binds one deployment and generation/config digest to an exact authorization action (`activate`, `rollback`, or restart `recover`) and the durable state sequence on which that decision was made, plus exact released Keyverse and Orgmetra authority coordinates, an immutable Orgmetra policy version, an authorization-decision digest, and one fresh `OwnerOperationObservation` for every admitted `(route, path, method, owner release/OpenAPI/artifact)` operation. The evidence provider receives that action and state sequence before making its decision; a generic allow for one generation cannot be silently relabeled as rollback authorization or replayed after the deployment state has advanced. Missing, duplicate, stale, future, wrong-action, wrong-state, wrong-generation, or wrong-owner operation evidence fails closed.

`AuthorizedPostgresActivationRegistry` obtains and validates remote evidence before the deployment row is locked. For activation and rollback, the structural registry persists or verifies the exact non-PII evidence material and appends the event in the same local transaction; PostgreSQL rechecks transition intent, state sequence, wall-clock expiry and exact operation coverage after any lock wait.

Authorized recovery uses a distinct evidence layer rather than rewriting the historical activation event. `recover_active()` first reads the active durable event/generation and requires the historical event to carry authorization evidence. It then obtains fresh `recover` evidence outside any database lock. `recover_active_authorized()` subsequently locks the same deployment, requires that the active activation sequence and generation are still exactly the ones externally verified, reconstructs the generation again, persists/verifies the fresh evidence bundle, and appends the next recovery attestation atomically. If the active state changed while remote verification was running, the locked recheck fails closed and no recovery evidence is committed. A successful restart decision therefore survives process exit and is auditable separately from the historical activation decision without holding network I/O under `FOR UPDATE`.

Structural `PostgresActivationRegistry.activate()` and `.rollback()` remain intentionally available inside the `activation` module as migration/fault-test primitives. They are deliberately **not re-exported from the package product API**; the root package exposes `AuthorizedPostgresActivationRegistry` for positive product activation/recovery. Current production schema enforcement through migration 0020 prevents an evidence-free structural event from becoming production activation history even though predecessor-schema tests retain the structural primitive.

This slice is still **not buyer-ready production activation authority**. Transaction-time activation and recovery evidence persistence, transition/recovery-intent enforcement, and database-clock freshness are represented, but the repository does not yet have the immutable external releases needed to drive a real positive path. Synthetic release locators or digests may exercise contract tests, but they are not buyer-ready authority.

Production completion still requires released Keyverse consumer evidence, immutable Orgmetra policy/release evidence, real downstream owner OpenAPI/behavior releases, a deployable HTTP composition host, security/fault/recovery evidence, supported deployment provenance, protected exact-head CI/review, and full buyer-path k6/E2E including the owner PostgreSQL path with the applicable p95 target.
