# Orgmetra product composition

This package is the first executable slice of the product-composition boundary tracked by #432. It decides whether configured product routes refer to exact immutable Orgmetra owner API releases before they are eligible for a composition generation. Route admission by itself is not buyer/product readiness.

A generation is bound to a deterministic digest of canonical semantic route material. `CompositionRoute` construction revalidates its nested `OwnerApiRelease`, so already-mutated or otherwise stale owner evidence cannot first become a route object and wait for later hashing to fail. Configuration identity is minted only after per-route and cross-route invariants pass. Owner release evidence must identify the canonical `ContextualWisdomLab/Orgmetra/releases/tag/<version>` coordinate, each `service_id` has one exact release/OpenAPI/artifact identity per generation, and each logical `service://` upstream must name that same owner service. Owner, route, and generation identifiers use canonical 1..64-character lower snake_case with no empty underscore-delimited segments; the mandatory `service://` projection uses the equivalent hyphenated form and therefore has the same representable identity domain. Mutable branches, floating labels, copied schemas, reachability-only checks, and digest-only pointers are not route authority.

## Supported OpenAPI route profile

Protected `docs/API_CONTRACT.md` remains the product contract and declares OpenAPI 3.2.0. OpenAPI Specification 3.2.1 is used here only as the current patch-level interpretation of the same 3.2 feature set; this canary is not a general OpenAPI parser and does not claim support for every path or operation form that OpenAPI 3.2 permits.

The admitted product-route dialect is intentionally narrower while no released owner contract requires a broader surface. A route path starts with `/v<digits>`, uses restricted ASCII literal segments, and uses a whole path segment for each canonical 1..64-character lower-snake-case template expression; repeated or trailing underscores therefore fail closed rather than becoming alternate parameter identities. The admitted method set is exactly `DELETE`, `GET`, `HEAD`, `OPTIONS`, `PATCH`, `POST`, and `PUT`. OpenAPI-valid forms outside that profile—including a template expression mixed with literals in one segment, percent-encoded or other unsupported `pchar` literals, and `TRACE`, `QUERY`, and `additionalOperations` methods—fail closed before configuration identity. Expanding the dialect requires released owner evidence plus explicit conformance tests; it is not inferred merely because a framework can route the form.

Route identity follows three separate layers:

1. **OpenAPI path-key identity.** OpenAPI Specification 3.2.1 §4.8.1 says templated paths with the same hierarchy but different template names are identical and MUST NOT coexist. `/v1/people/{person_record_id}` and `/v1/people/{worker_record_id}` therefore cannot both acquire configuration identity, even when their HTTP methods differ. Distinct methods may share the same exact template string only within one exact owner release in the current Orgmetra profile. OpenAPI's Path Item Object also carries path-level `$ref`, `summary`, `description`, `servers`, and `parameters`; `servers` services all operations on the path and path-item parameters apply to all operations. The current composition canary has no cross-owner Path Item merge or conformance contract, so splitting one exact path across owner releases would make those shared semantics unverifiable.
2. **OpenAPI path matching.** The same section, with §4.8.2.1's examples, gives a concrete non-templated path precedence over its templated counterpart and treats ambiguous templated matching as tooling-dependent. Path selection therefore cannot be made safe merely because two overlapping routes use different HTTP methods: the Path Item is selected before an operation on it is meaningful. The admission model permits different overlapping path strings only for the deterministic concrete-before-template case when both routes belong to the same exact owner release and declare the same method set. Thus one owner may publish `GET /v1/people/current` beside `GET /v1/people/{person_record_id}`. Cross-owner concrete/template overlap, same-owner concrete/template overlap with different method sets, and ambiguous overlap between two templated paths all fail before configuration identity, even when the routes' methods are disjoint.
3. **HTTP operation authority.** Only after Path Item ownership and path matching are deterministic does operation collision matter. Distinct methods may coexist on one exact path only under the same exact `OwnerApiRelease`. For overlapping effective operations, RFC 9110 makes GET and HEAD one selected-resource collision authority while the methods actually declared remain exact contract material.

The one-owner-per-Path-Item rule is an Orgmetra fail-closed product decision, not a claim that OpenAPI itself assigns repository or bounded-context ownership. A future released composition contract may broaden this only if it defines and tests how every path-level field and operation from multiple owner descriptions is combined without ambiguity.

OpenAPI 3.2.1 §4.8.2 also says each template expression MUST NOT appear more than once in one path template, so `/v1/tenants/{record_id}/people/{record_id}` fails before hashing/admission. Complete RFC 3986 `.` and `..` path segments are rejected rather than normalized into another route identity.

The composition contract has no local retry class, idempotency mode, concurrency mode, HR authorization policy, or scientific truth. Those semantics remain with released owner contracts. `AdmissionReceipt` is issued only by the canonical in-process evaluator; its exact fields and source generation are leased in process-local closure state. Receipt validation rechecks the source generation, nested owner/route evidence, and canonical configuration digest, so post-issuance source mutation invalidates stale evidence.

A canonically constructed `CompositionGeneration` retains a process-local construction snapshot of schema/generation/config identity. One live process cannot give the same `generation_id` two configuration meanings while generation views or canonical receipts remain live. This is not durable allocation authority: after GC/process restart only a future immutable activation/configuration registry can prove historical no-reassignment across deployment lifetimes.

Current scope is transport-neutral and performs no network I/O, authentication, HR-domain authorization, database access, or retry execution. Production completion still requires released Keyverse consumer evidence, Orgmetra identity ACLs, real downstream owner OpenAPI/behavior releases, a deployable HTTP composition host, durable activation/rollback re-admission, security/fault/recovery evidence, supported deployment provenance, protected exact-head CI/review, and full buyer-path k6/E2E including the owner PostgreSQL path with the applicable p95 target.
