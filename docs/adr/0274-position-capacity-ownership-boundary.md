# ADR 0274: Separate Position ownership with a fenced capacity protocol

## Status

Proposed — active PR only. This ADR is not protected `develop` truth and does not authorize source extraction until the prerequisite owner stack is normally integrated and the distributed invariant has executable evidence.

## Context

Protected `ARCHITECTURE.md` and `docs/TRD.md` assign Position truth to `organization_core` while `people_core` owns Person, Employment, and Assignment. The executable protected tree does not yet have an `organization_core` service owner; the shipped People mutation boundary still creates Position and serializes Assignment capacity against the Position root. Issue #274 tracks this accepted-architecture versus executable-owner gap.

ADR 0004 already makes `position_record` a durable anchor with bitemporal versions and binds Assignment to Employment, Person, and Position. ADR 0005 already requires Assignment days to be covered by an `active` or `open` Position version and visible allocation for one Position seat to remain at or below `1.0000`. This ADR preserves those semantics. It decides only how Position write/capacity authority can move to `organization_core` without adding cross-service SQL, a second Position writer, or a checked-versus-used race.

PostgreSQL 18 `READ COMMITTED` gives each command a new committed snapshot. A read-only availability check followed by a separate People write therefore does not, by itself, preserve the cross-row seat invariant. PostgreSQL row locks can serialize writers inside one database owner, but service extraction requires an explicit cross-context protocol rather than assuming one local transaction.

A second distributed race exists after a capacity debit is fenced. A point-in-time People read that currently finds no Assignment is not proof that a delayed or in-flight `create_assignment` operation cannot commit later. Releasing capacity from that observation can therefore re-open the seat before the original Assignment commits. Post-fence release needs a terminal People-owned attempt outcome that also fences every later commit for the same attempt.

A third race exists if Position eligibility is treated as a mutable read after the capacity fence. An authentic fence issued while the required Position coverage is `active` or `open` cannot remain safe if Organization may independently commit an overlapping `closed` or otherwise ineligible Position version before People commits Assignment. A People-side recheck does not solve this because Position can change again after the recheck. The Organization reservation therefore has to fence both seat capacity and the Position eligibility required by ADR 0005 for the reservation interval.

Protected assignment validation already accepts a union of visible staffable Position versions when that union covers the whole Assignment interval. A reservation interval may therefore legitimately cross one or more Position-version boundaries while remaining continuously eligible. A single `position_record_version_id` is not sufficient eligibility evidence for that case. The fenced protocol must preserve the canonical visible coverage set, not collapse it into one version identifier.

A separate operability and correctness hazard appears if the Organization transaction tries to solve those races by calling People while holding the Position row lock. PostgreSQL row locks last until transaction end; a remote call under that lock couples database lock lifetime to network/provider latency, enlarges deadlock and pool-exhaustion surfaces, and turns a local aggregate transaction into an implicit distributed lock. Cross-context coordination must therefore occur outside the Position-locking transaction. The local transaction may accept, fence, confirm, release, adjust, or reject from already durable evidence; it may not wait on People while the Position lock is held.

The same evidence rule is required after the initial Assignment is confirmed. A current People read showing a shorter interval, smaller allocation, different Position, ended Assignment, or no row is not sufficient authority to shrink or release an Organization-owned confirmed debit. A delayed correction, retry, conflicting revision, or stale projection could otherwise reopen capacity while the still-authoritative Assignment version remains effective. Every capacity-affecting Assignment mutation therefore needs terminal, immutable People-owned mutation evidence, and any mutation that increases required capacity must fence the positive capacity delta before People can commit it.

Binding a revision command to a prior Assignment version is also insufficient unless People enforces that version as a compare-and-set precondition. Two distinct mutation attempts can otherwise both be prepared against V1, obtain separate valid Organization delta fences, and both commit because locking only their distinct `assignment_attempt_id` values does not serialize the Assignment lineage. Capacity evidence can remain individually authentic while the People history forks. Every revision/end transaction therefore serializes the stable Assignment root and requires its exact expected prior version to remain authoritative at the write linearization point; a stale-predecessor attempt becomes terminally non-committing and its unused delta fences can be released only from that terminal outcome.

Assignment-root serialization alone does not protect the ADR 0004 Employment allocation rule for creates on different Positions or different Assignment roots. Two distinct create attempts can each reserve `0.6000` on separate Positions, then both validate the same prior Employment portfolio and commit `1.2000`. Every Assignment mutation that changes one Employment's visible allocation therefore also serializes the stable Employment root and re-reads the authoritative overlapping Assignment portfolio before commit. Existing-Assignment mutations use the deterministic local lock order Employment root then Assignment root.

A revision can also become under-reserved when Organization settlement lags People history. If V1=`1.0000` is revised to V2=`0.5000` but Organization still carries V1's confirmed debit, a V3 increase back to `1.0000` must not infer a zero delta from that lagging ledger and then allow the delayed V2 receipt to shrink the backing to `0.5000`. A capacity-affecting successor revision is therefore admitted only from an exact predecessor Assignment version whose Organization backing has already reached settlement equivalence and produced an authenticated settlement receipt. Positive deltas are computed from that settled predecessor backing, not from arbitrary currently visible ledger residue.

Source extraction also needs a real linearization point. Merely rejecting new Assignment commands and then projecting the database is unsafe if a legacy People transaction was admitted before the fence and commits after the projection snapshot. The cutover barrier must reject new legacy admissions and wait until every transaction admitted before the fence has either committed or rolled back before any authoritative migration snapshot is taken.

Transaction drain alone is not enough for a later authority/rollback epoch transition once the cross-context protocol is live. A valid epoch-E `commit_fenced` reservation can exist without an open database transaction or terminal People outcome. If rollback snapshots Assignment history and then supersedes E, that unresolved debit has no lossless legacy projection while a delayed People mutation may still hold authentic E write authority. Stale-epoch rejection after the switch can prevent new mutation, but by itself it can also strand the unresolved debit; if People has not yet adopted the new epoch, a delayed mutation can commit after the rollback snapshot. Retiring an epoch therefore requires a protocol-quiescence barrier in addition to local transaction drain.

The retirement barrier must cover both owners. Rejecting new Organization reservations after setting `draining(E)` is not enough if an Organization transaction was already admitted under E and can commit a new reservation or fence after the quiescence manifest. Likewise, proving quiescence and then incrementing an epoch without durable arbitration permits two concurrent rollover controllers to activate different target writers. Admission receipts cannot retroactively acquire a transition identity that did not exist when they were issued. Each owner therefore maintains a pre-existing source-epoch admission sequence. The unique transition lineage is acquired first; Organization and People then each close their own source-epoch business-admission gate and capture their own local high-water by owner-local compare-and-set. Each owner publishes one authenticated source-boundary closure receipt bound to the transition lineage, source pair, gate version, captured mark, and the retry generation in which that gate was first closed as provenance. There is deliberately no cross-service atomic close: quiescence cannot proceed until both closure receipts are durable, and any transaction admitted by the owner that closes later is included at or below that owner's captured high-water. Because an abort/retry never reopens source business admission, those closure receipts and high-water marks remain stable lineage boundary evidence across retry generations; a later generation must recompute fresh drain, reconciliation, settlement, and quiescence proof from authoritative state rather than minting fictitious replacement closure receipts. This preserves the no-distributed-ACID boundary while covering both the inter-owner closure gap and retry-generation evidence isolation.

Closing ordinary mutation admission cannot also close the operations needed to settle already-admitted work. After the captured business-mutation drains are terminal, an unresolved E `commit_fenced` attempt may still require People `terminalize_attempt` and Organization confirm/release/apply-revision transactions. If those recovery writes had to obtain the now-closed ordinary E admission, retirement could deadlock forever. The transition therefore owns a separate, obligation-bounded reconciliation lane. That lane may act only on the exact retiring-epoch attempts/reservations/receipts in the transition recovery work ledger; it cannot reserve new capacity, arm a new fence, create/revise an Assignment, or change unrelated Position truth. Its own receipts are transition- and retry-generation-bound, monotonically sequenced, and must themselves be closed, high-water captured, and drained before quiescence.

Cutover cannot assume the legacy snapshot is valid merely because the legacy writer is authoritative. If the drained snapshot already contains over-allocation, incomplete staffable Position coverage, malformed tenant/identity evidence, or another condition that cannot satisfy ADR 0004/0005 and the new reservation ledger simultaneously, silently dropping, clamping, splitting, rounding, or otherwise normalizing records would create a new truth rather than migrate the old one. Such a discrepancy is a fail-closed cutover finding: authority does not switch until the legacy truth is explicitly corrected under governed ownership and the projection is rerun.

Protected `docs/TRD.md` also preserves retroactive correction as an authoritative bitemporal operation: a correction closes the superseded recorded interval and inserts replacement truth for an earlier effective period. The capacity ledger therefore cannot migrate only assignments whose effective intervals are current or future at cutover. Omitting a wholly past but currently recorded-visible Assignment would make a later retroactive create/correction validate against an incomplete Position occupancy history and could authorize more than `1.0000` on that historical slice. Cutover must project the complete currently authoritative effective-time domain needed by post-cutover retroactive writes; superseded recorded-history versions remain People/audit evidence but do not become duplicate live capacity debits.

## Decision drivers

The design must:

- keep Position and Position capacity as Organization-domain truth while keeping Assignment history as People-domain truth;
- preserve the bitemporal and allocation semantics already Accepted in ADR 0004/0005;
- expose one canonical capacity/eligibility authority without cross-service application-table access;
- remain correct under concurrent claims, retries, delayed requests, process loss, message loss/duplication/reordering, ambiguous timeouts, concurrent Position mutation, concurrent Assignment revisions, Assignment correction/end races, and authority/rollback epoch transitions;
- bind idempotency to semantic intent and `assignment_attempt_id`, rather than a caller-controlled key alone;
- authenticate cross-context receipts with issuer, audience, tenant, authority/rollback epoch, exact target version/digest, replay-safe receipt identity, and a signing-key version authorized for the claimed epoch and write purpose before they become write authority;
- serialize every Assignment allocation change at the stable Employment root and revalidate the ADR 0004 Employment portfolio, with existing-Assignment mutations additionally serializing the stable Assignment root and compare-and-setting the exact expected prior Assignment version;
- require authenticated Organization settlement equivalence for the exact predecessor Assignment version before admitting another capacity-affecting revision;
- distinguish terminal People mutation evidence from point-in-time reads or absence observations;
- make a post-fence receipt durable evidence of both consumed capacity and complete Position eligibility coverage for its effective interval;
- require positive capacity/eligibility deltas for Assignment revisions to be fenced before the People revision can commit;
- permit capacity decreases/releases only from immutable terminal People revision/end evidence bound to the exact superseded Assignment and reservation versions;
- keep remote service I/O outside Position-root, Employment-root, and Assignment-root transactions and row-lock lifetimes;
- make migration linearizable against legacy in-flight writes and deterministically reproducible from tenant-qualified legacy identities;
- quiesce both owners' old-epoch business-mutation admissions and cross-context protocol state before retiring write authority, using pre-existing owner-local admission sequences, owner-local admission-close CAS/high-water receipts, and a two-sided closure barrier rather than retroactive transition binding or a fictitious cross-service atomic close;
- retain source-pair admission-closure receipts/high-water marks as lineage-stable boundary evidence across retries while requiring fresh generation-scoped drain/reconciliation/settlement/quiescence proof;
- retain a transition-scoped, obligation-bounded reconciliation lane after business-mutation admission closes, prohibit that lane from creating new domain work, and drain its own generation-bound admissions before quiescence;
- arbitrate each live authority/rollback rollover through one durable transition lineage CASed from the exact current epoch pair so only one target writer can activate, including abort/retry without source-pair ABA or a second lineage;
- prohibit abort of a retry generation while either owner has a nonterminal captured admission receipt, an open retirement-reconciliation receipt, or unapplied capacity-changing settlement obligation;
- preserve currently authoritative past-effective occupancy required for retroactive bitemporal correction rather than treating cutover time as an effective-time retention boundary;
- make migration lossless and fail closed when authoritative legacy occupancy cannot satisfy the target invariants without semantic rewriting;
- minimize PII at the Organization boundary; and
- support a fenced cutover from the existing same-database People mutation path without a dual-writer interval.

## Alternatives

### A. Move Position and Assignment into one Organization aggregate/service

This gives the simplest local transaction for seat allocation, but it moves worker Assignment history out of the protected `people_core` ownership model and couples employment-lifecycle truth to structural Organization ownership. Reject for now.

### B. Keep Position in Organization and call a synchronous availability read before People writes Assignment

This preserves nominal ownership but is not sufficient for correctness. Between availability read and Assignment commit, another writer can consume the same capacity or change Position eligibility. Reject as a TOCTOU design.

### C. Organization-owned `PositionCapacityReservation` with commit fences and People-owned terminal mutation outcomes

Provisionally selected. `organization_core` is the sole writer for Position status/version and Position capacity. `people_core` remains the sole writer for Assignment history and for terminal outcomes of capacity-affecting Assignment mutation attempts. Their shared invariant is represented by a versioned protocol rather than cross-service SQL.

### D. Two-phase Assignment visibility

People first stores an Assignment in a non-active `pending_capacity` state, Organization confirms capacity, and People then activates it. This avoids a non-expiring unresolved capacity debit but adds another authoritative Assignment lifecycle state plus activation/reconciliation failure windows. Keep as the principal alternative until option C has executable failure evidence; do not mark this ADR Accepted merely because option C is currently preferred.

## Domain model and ubiquitous language

`organization_core` owns:

- `Position`: aggregate root for one tenant-qualified staffable seat and its bitemporal status/version evidence.
- `PositionCapacityReservation`: entity under Position capacity authority. It binds an opaque reservation identifier, tenant, Position, allocation ratio, effective interval, opaque `assignment_attempt_id`, assignment mutation intent/reference, canonical Position eligibility coverage evidence, idempotency key, semantic command digest that includes the exact `assignment_attempt_id`, lifecycle state, predecessor/supersession evidence where applicable, owner authority/rollback epoch, and immutable audit/outbox correlation.
- `PositionEligibilityCoverage`: value object containing the canonical ordered set of visible Position-version interval slices whose union covers the reservation interval at the fence's knowledge cutoff. Each element carries the exact `position_record_version_id` and intersecting valid-time slice; the normalized set and cutoff are digest-bound.
- `EpochAuthorityTransition`: durable recovery entity and unique transition lineage for one exact source `(authority_epoch, rollback_epoch)` pair. It binds transition identity, monotonically increasing retry generation, canonical target writer and target epoch pair, transition digest, state (`draining`, `quiesced`, `activated`, or `aborted`), Organization and People source-epoch admission-closure receipt identities/digests, their owner-local business-admission high-water marks and first-close retry-generation provenance plus generation-scoped drain proofs, a transition-scoped reconciliation work-ledger digest, reconciliation admission sequence/high-water/drain proof, quiescence-manifest digest, expected transition version, and immutable activation receipt. Each owner issues ordinary transaction-lifetime admission receipts from a pre-existing monotonic source-epoch admission sequence before any transition exists. Creating generation 1 acquires only the source-pair-unique transition lineage and immutable target intent. Organization and People then independently CAS their own E admission gates from open to closed, capture their own local high-water in the same local transaction, and publish authenticated closure receipts bound to the transition identity, source pair, gate version, captured mark, and `closed_at_retry_generation`. Neither owner calls or writes the other owner's database while holding that local gate transaction. The transition does not treat business admission as closed until both authenticated closure receipts are present and consistent. A request admitted in the interval between the two local closes is covered by the later owner's captured high-water; a request arriving after an owner's local close cannot obtain that owner's E admission sequence. Every ordinary receipt at or below a captured mark is then a drain obligation whether or not it could name the transition. The closure receipts and captured marks are immutable source-boundary facts for the transition lineage: after an abort, later retry generations reference those same receipts because the source business gates remain closed, while recomputing fresh generation-scoped drain proof from the authoritative admission ledgers. After both drains are terminal for the active generation, the transition may admit only recovery actions bound to that generation's freshly derived retiring-epoch work ledger: terminalize an already-known unresolved attempt, apply an already-durable or resulting terminal receipt to its exact reservation/version, or complete exact confirm/release/revision settlement. Recovery admission carries transition identity, retry generation, exact obligation identity/digest, and a monotonic reconciliation sequence; it cannot create new reservation/fence/Assignment/Position business truth. Before `quiesced`, reconciliation admission is closed, its high-water is captured, every receipt through that mark is terminal, the work ledger is exhausted, and cross-owner equivalence is rechecked. The source pair has at most one transition lineage across every state; `aborted` does not release the source-pair uniqueness claim or permit a second transition row. Creation, retry-generation admission proof, quiescence, abort, and activation use expected-version compare-and-set. An equivalent retry after `aborted` may CAS the same transition identity from `aborted` back to `draining`, increment retry generation, and recompute fresh drain/settlement proof from current source truth only when the source pair is still current, source business admission remains closed at both owner-local gates, both immutable closure receipts remain consistent with their captured marks, no activation receipt exists, both captured owner admission ledgers are currently terminal through those marks, the prior reconciliation lane is closed and drained, all capacity-changing settlement obligations are terminally applied, and target writer/target epoch/digest are byte-equivalent to the original intent. It does not re-close either business gate or mint replacement closure receipts. Contradictory target/digest intent cannot repurpose the aborted lineage and fails closed until authority is refreshed through a separately governed decision.
- `AllocationRatio` and `EffectiveInterval`: value objects used to calculate overlapping capacity.

`people_core` owns:

- `Employment`: stable People aggregate root and serialization boundary for the ADR 0004 multiple-membership Assignment allocation portfolio. Every create, revise, move, shorten, or end operation that can change one Employment's effective allocation obtains this root before validating and committing that portfolio.
- `Assignment`: aggregate-root history fact bound to tenant, Employment, Person, Position, allocation, effective interval, and the exact Organization capacity/eligibility evidence that authorized the effective write. Capacity-affecting revisions serialize the Employment root and then this stable Assignment root, compare-and-set the exact expected prior Assignment version, and require the predecessor version's exact authenticated Organization settlement receipt before a new authoritative version/end can commit.
- `AssignmentAttemptOutcome`: terminal, tenant-qualified protocol evidence for one opaque `assignment_attempt_id`. Each capacity-affecting create, revise, move, shorten, or end attempt gets its own attempt identity. The semantic digest binds operation kind, the exact `assignment_attempt_id`, exact stable Employment identity and expected portfolio version/digest, exact stable Assignment identity and expected prior version when one exists, exact predecessor Organization settlement receipt when one exists, exact prior Organization reservation version/digest set, requested resulting Assignment facts, and each new Organization delta-fence receipt with its target reservation identity/version/digest. The terminal outcome records every referenced fence disposition as `consumed` or `unused_releasable`; Organization must compare-and-set the expected reservation version before confirming or releasing that fence. Its terminal state is `committed` with the authoritative resulting Assignment version/end receipt or `aborted` with an immutable abort/conflict tombstone. A terminal `aborted` outcome fences every later retry for that same attempt from committing.

No Person name, compensation, rating, assessment result, or other worker payload is copied into `PositionCapacityReservation`. The cross-context protocol carries only opaque references, semantic digests, normalized eligibility coverage evidence, and terminal receipts required to enforce the seat invariant.

## Capacity and Position-eligibility invariants

While a reservation debit is effective, `held`, `commit_fenced`, and `confirmed` states consume capacity. `released`, `expired`, and `cancelled` states do not. Only `held` may expire autonomously.

For every tenant-qualified Position and every overlapping valid-time slice:

`sum(allocation_ratio for effective held + commit_fenced + confirmed reservation debits) <= 1.0000`

For every tenant-qualified Employment and every overlapping valid-time slice, the authoritative People Assignment portfolio independently preserves ADR 0004:

`sum(allocation_ratio for visible authoritative Assignments of one Employment) <= 1.0000`

Every effective `commit_fenced` or `confirmed` debit also requires Organization-owned Position state to remain assignment-eligible (`active` or `open` under ADR 0005) for its interval. Its `PositionEligibilityCoverage` must cover that entire interval as a normalized union; a Position mutation that would invalidate any covered slice while such a debit exists cannot commit as an unrelated independent change.

For an Assignment revision, Organization computes capacity by effective Position/time slice from the exact settled predecessor Assignment backing. A successor capacity-affecting revision is not admitted while the predecessor Assignment version's Organization settlement is pending. Existing confirmed debits remain authoritative until immutable People evidence allows their reduction or release. After predecessor settlement, any positive delta between the proposed resulting Assignment occupancy and that exact predecessor backing must be represented by one or more new `held -> commit_fenced` debits before People may commit the successor revision. Decreases need no speculative release before People commit; temporary over-reservation is safe, while temporary under-reservation is not.

`organization_core` enforces Position rules by serializing reservation and Position-status/version mutations at the stable Position root and re-reading authoritative overlapping debit and Position-version sets inside that local transaction. `people_core` serializes every allocation-changing Assignment mutation at the stable Employment root and re-reads the authoritative overlapping Assignment portfolio; existing-Assignment mutations then acquire the stable Assignment root in the fixed Employment-before-Assignment order and reject a revision whose expected prior version is no longer authoritative. A stale read model is never capacity, eligibility, Employment-allocation, or Assignment-lineage authority, and neither owner performs cross-context I/O while holding its local root lock.

## Protocol

1. `reserve`: under Position-root serialization, validate Position status/version coverage and capacity, then create `held`. The idempotency record is tenant-qualified and stores the idempotency key, exact `assignment_attempt_id`, semantic command digest, resulting reservation identity/version, and issuing authority/rollback epoch. The semantic digest itself includes the exact `assignment_attempt_id`. Exact replay of the same key, attempt ID, digest, and epoch returns the same reservation; the same key with a different attempt ID, digest, or authority context fails closed.
2. `arm_commit_fence`: under the same Position-root authority, compare-and-set the exact expected reservation version and verify that the stored `assignment_attempt_id`, semantic digest, and authority epoch still match the command. Revalidate capacity and complete `active`/`open` coverage for the exact effective interval, normalize `PositionEligibilityCoverage`, and convert `held` to `commit_fenced`. This is durable, idempotent for the same reservation version/attempt/digest, coverage-digest-bound, non-expiring, and becomes an Organization promise not to commit an incompatible Position-status/version transition while the debit remains `commit_fenced` or `confirmed`. A mismatched attempt ID, digest, expected version, or retired epoch fails closed.
3. `create_assignment`: after the Organization transaction has completed, People accepts only a verified cross-context Organization receipt proving the exact reservation is `commit_fenced` for the same tenant, Position, allocation, effective interval, semantic intent, complete Position eligibility coverage digest, `assignment_attempt_id`, reservation version/digest, and currently admitted authority epoch. Receipt verification follows the authenticated-envelope contract below before the receipt can authorize a People write. Inside one People transaction, it serializes the attempt identity and stable Employment root, re-reads the authoritative overlapping Assignment portfolio, and rejects any result whose Employment allocation would exceed `1.0000` on an effective slice. It then either writes Assignment plus terminal `AssignmentAttemptOutcome=committed` atomically, returns the existing equivalent terminal outcome, or fails closed on contradictory evidence. Distinct attempts on different Positions still contend on the same Employment root. A terminal `aborted` attempt can never later commit.
4. `terminalize_attempt`: reconciliation may ask People to resolve an exact unresolved attempt. People serializes on `assignment_attempt_id`; if that attempt already committed, it returns the terminal `committed` outcome. Otherwise it writes a durable terminal `aborted` tombstone that prevents every delayed or retried mutation for that attempt from committing. A point-in-time `not found`, empty result, HTTP timeout, or missing event is not a terminal outcome. During epoch retirement this operation is admitted only through the transition-scoped reconciliation lane for an exact work-ledger obligation; the closed ordinary E mutation lane cannot be used to create unrelated terminalization work.
5. `confirm`: in a new Organization transaction, Organization converts `commit_fenced` to `confirmed` only from an already-obtained and authenticated terminal People `committed` receipt for the exact attempt/reservation/version/digest. The receipt's fence disposition must mark that target as `consumed`, and Organization compare-and-sets the exact expected reservation version. Duplicate or reordered equivalent confirmation is idempotent; stale version, contradictory disposition, different digest, or retired authority context fails closed. Once all backing for the exact resulting Assignment version is applied and equivalent to its terminal People evidence, Organization publishes an authenticated `AssignmentCapacitySettlement` receipt binding that Assignment version, backing reservation identity/version/digest set, effective occupancy, owner authority/rollback epoch, and settlement digest. The Organization transaction does not call People while holding the Position lock. During epoch retirement, exact confirm/settlement work for captured E obligations uses the transition-scoped reconciliation lane and cannot originate new capacity work.
6. `revise_assignment_capacity`: each capacity-affecting correction, move, interval change, allocation change, or end is a new People mutation attempt bound to the stable Employment identity, stable Assignment identity, exact expected prior Assignment version, and exact prior reservation evidence. Before requesting a successor fence, the caller must obtain an authenticated Organization `AssignmentCapacitySettlement` receipt proving that every capacity disposition for the exact predecessor Assignment version has been applied and that Organization backing is equivalent to that predecessor's authoritative occupancy. A missing, stale, or mismatched settlement receipt blocks the successor mutation; a lagging Organization ledger is never used to infer a smaller positive delta. Organization then reserves and arms all positive target capacity/eligibility deltas relative to the exact settled predecessor backing. For a same-Position increase this may be only the additional allocation/time slices; for a Position move it is the full target occupancy not already backed on the target Position. People then starts one local transaction, serializes the mutation attempt, stable Employment root, and stable Assignment root in that order, re-reads the Employment portfolio, verifies the expected prior Assignment version and settlement receipt are still authoritative, and only then atomically writes the new Assignment version/end plus terminal `committed` outcome. If another mutation already advanced the Assignment lineage or Employment portfolio, this attempt cannot commit from stale evidence; it records/returns terminal non-committing `aborted` conflict evidence so any unused delta fences can be released idempotently. The caller must start a new attempt against current authoritative evidence rather than replaying the stale command under a new key.
7. `apply_revision_receipt`: after People commits a revision/end, Organization applies the already-obtained authenticated terminal receipt in one or more new Position-local transactions. Each fence transition is bound to the receipt's exact target reservation identity/version/digest and `consumed` or `unused_releasable` disposition, and Organization compare-and-sets that expected reservation version. New delta fences are confirmed before superseded debits are reduced/released. Across a Position move, target capacity is therefore confirmed before source capacity is released. Same-Position incremental debits may remain as multiple confirmed ledger entries whose effective sum equals the new Assignment occupancy; later compaction, if implemented, must be evidence-preserving and cannot change effective capacity. Only after all required dispositions have been applied and Organization backing equals the exact resulting Assignment version may Organization emit its `AssignmentCapacitySettlement` receipt. Older duplicate revision receipts then replay idempotently or fail exact-version CAS; they cannot reduce the backing of a later settled version. A confirmed debit is never shrunk or released from a mutable People read, current absence, timeout, event-delivery state, elapsed time, or a receipt from a retired epoch. During epoch retirement, applying exact already-captured E dispositions is transition-scoped reconciliation, not ordinary E business admission.
8. `release_uncommitted`: an ordinary `held` reservation may be released or expire before a commit fence. A `commit_fenced` debit for an unresolved or stale-predecessor-aborted attempt may return capacity only from an already-obtained authenticated terminal People `aborted` receipt for the exact attempt and target reservation identity/version/digest whose disposition is `unused_releasable`. Applying the durable receipt compare-and-sets that reservation version in a local Organization transaction; obtaining and authenticating it happens outside the Position lock. During epoch retirement, exact release of a work-ledger obligation is allowed only through the transition-scoped reconciliation lane.
9. `change_position_status_or_version`: Organization serializes the proposed mutation at the same Position root. If the change would remove eligible coverage from any slice consumed by `commit_fenced` or `confirmed` debits, this transaction fails closed with durable conflict/audit evidence and ends without making a People call. A separate governed workflow may then terminalize or correct affected People attempts/Assignments outside any Position lock, apply resulting terminal receipts in new local Organization transactions, and retry the exact status/version command against the new Position/reservation version.

### Authenticated cross-context receipt envelope

Capacity, settlement, and terminal-outcome receipts are durable write authority, so transport authentication alone is insufficient once a receipt is persisted, queued, or replayed. Both directions use a versioned canonical envelope whose signed fields include `contract_version`, globally unique `receipt_id`, `issuer_context`, `audience_context`, tenant, monotonic owner `authority_epoch`, monotonic `rollback_epoch`, immutable `key_id`/key version, exact `assignment_attempt_id` where applicable, semantic command digest, issued receipt version, and canonical payload digest. Organization capacity payloads additionally bind Position, effective interval, allocation, reservation identity/version/state, and `PositionEligibilityCoverage` digest. Organization settlement payloads bind the exact resulting Assignment version and complete backing reservation identity/version/digest set. People terminal payloads bind stable Assignment identity, expected prior/resulting Assignment version, exact prior and target reservation identity/version/digest set, and each fence disposition.

The canonical owner signs the canonical envelope with an owner-controlled asymmetric signing key. The released, versioned verification-key manifest binds each immutable `key_id`/version to the expected issuer identity, an allowed authority/rollback-epoch range or explicit epoch-pair set, and a purpose class such as `domain_transition` or `audit_only`. Before any domain transition, the consumer must both verify the signature and verify that the referenced key version is authorized for the receipt's claimed issuer, authority/rollback epoch, and `domain_transition` purpose. Keyverse-backed service identity and mutually authenticated transport may authenticate the live channel, but neither substitutes for receipt integrity after transport. A receipt whose signature, key authorization, issuer, audience, tenant, owner epoch, rollback epoch, contract version, target reservation/Assignment version, or digest does not match the consumer's pinned authority state fails closed.

Replay protection is idempotency-preserving rather than timeout-based: byte-equivalent replay of the same `receipt_id` and canonical payload may return the same result while that authority epoch remains admitted or after the same terminal result is already durably recorded; reuse of that `receipt_id` with a different canonical payload, attempt ID, target, version, digest, issuer/audience, tenant, or authority epoch is contradictory evidence and fails closed. A retired authority/rollback epoch cannot authorize a new domain transition even when the signature is otherwise valid. Historical verification keys may remain available for audit, but once retired from write authority they are marked `audit_only` or otherwise excluded from every current `domain_transition` epoch binding. A cryptographically valid payload signed by a historical or compromised old key while claiming a current epoch therefore fails key-authorization validation before domain mutation.

A timeout may enqueue reconciliation; it may not undo a commit fence, shrink a confirmed debit, infer a terminal People state, advance an authority epoch, or satisfy predecessor capacity settlement. No remote timeout extends a Position, Employment, or Assignment database lock because cross-context calls are never made from any root-locking transaction.

## Failure and recovery semantics

- Crash after `held` but before commit fence: bounded expiry may reclaim capacity.
- Crash after commit fence before People receives or commits the mutation: capacity and Position eligibility stay fenced. Reconciliation may terminalize the attempt, but release occurs only after People durably records `aborted` and thereby fences all future commits for that attempt.
- Delayed/in-flight mutation racing `terminalize_attempt`: People serializes both by `assignment_attempt_id`, so exactly one terminal outcome wins.
- Two distinct Assignment creates for one Employment, even on different Positions: People serializes the stable Employment root and re-reads the authoritative portfolio. At most one can commit if both `0.6000` claims would produce `1.2000`; the loser becomes terminally non-committing and its unused Position fence remains reserved until exact abort/conflict evidence is applied.
- Two distinct revisions prepared from the same prior Assignment version: each may have authentic delta fences, but People serializes the stable Employment root and stable Assignment root and compare-and-sets the expected predecessor. At most one can advance that lineage from the same version. The loser becomes terminally non-committing and its unused delta fences remain reserved until Organization receives the exact authenticated abort/conflict receipt with matching reservation versions and `unused_releasable` dispositions.
- Crash after People commits Assignment plus terminal `committed` outcome but before Organization receives `confirm`: capacity and Position eligibility stay fenced; a second overlapping claim that would exceed `1.0000` is rejected. Reconciliation confirms from authoritative People evidence.
- Allocation increase or interval extension: the positive delta is fenced before People commit. A crash after People commit but before delta confirmation leaves both old confirmed occupancy and the new delta commit-fenced, so capacity remains conservative rather than under-reserved.
- Successor revision while predecessor settlement is pending: fail closed before successor admission. For V1=`1.0000` -> V2=`0.5000` -> V3=`1.0000`, V3 cannot treat the still-visible V1 ledger debit as V2 backing; it waits for the exact V2 settlement receipt, then fences the `0.5000` positive delta. A delayed duplicate V2 receipt cannot later shrink V3 backing because exact reservation-version CAS and settlement-version binding reject or idempotently replay it.
- Allocation decrease, shortening, or end: People may commit first, but the old confirmed debit remains until the terminal revision receipt is applied. A crash in that window causes temporary under-utilization, not overbooking, and no successor capacity-affecting revision is admitted until that version settles.
- Position move: target capacity/eligibility is commit-fenced before People commit; after People commit, Organization confirms target evidence before releasing source evidence. Crashes or reordered delivery can temporarily reserve both Positions but cannot leave the moved Assignment without target capacity/eligibility.
- Stale or duplicated revision receipt: the receipt is authenticated and bound to exact prior Assignment and reservation versions/digests plus fence dispositions. It either replays idempotently or fails closed; it cannot release a debit superseded by a different authoritative revision.
- Forged, wrong-audience, cross-tenant, stale-epoch, rollback-epoch, replay-with-different-payload, mismatched-target, or key-not-authorized-for-claimed-epoch/purpose receipt: reject before the receipt can authorize a People or Organization transition; record fail-closed security/audit evidence.
- Position status/version mutation racing a fenced Assignment attempt: the local Organization mutation serializes against the same Position root and live debit set. If the proposed change would make an effective slice ineligible, it exits with conflict rather than calling People under the lock.
- Crash during external Position-change coordination: the original Position eligibility coverage/fence remains authoritative because the rejected Organization transaction made no eligibility change. Idempotent People terminalization/correction and Organization receipt application can resume without a distributed lock.
- Lost, duplicated, or reordered confirm/release/revision messages: authenticated attempt/reservation version, semantic digest, fence disposition, receipt identity, and authority epoch preserve one result or fail closed on contradiction.
- Epoch retirement with unresolved protocol state: the authority switch stays blocked. Old-epoch state is settled under a protocol-quiescence barrier before the epoch is superseded; stale-epoch rejection is not used as a substitute for settlement.
- Transition creation versus already-admitted transactions: pre-existing source-epoch admission receipts are covered by each owner's locally captured high-water mark, not retroactively rebound to a new transition identity. The transition is unique, but the two owner admission gates close independently. Work admitted by the later-closing owner remains a captured drain obligation; quiescence cannot begin until both authenticated closure receipts exist and every receipt at or below both captured marks is terminal.
- Retry after a fully drained abort: the same source-pair admission-closure receipts and captured high-water marks remain authoritative because neither source business gate reopens. Their `closed_at_retry_generation` is provenance, not proof freshness. The new retry generation must freshly re-read both admission ledgers through those marks and produce its own drain proof; prior reconciliation, settlement, work-ledger, and quiescence proof artifacts remain historical only.
- Retirement after ordinary admission closes: unresolved captured work is settled through the transition-scoped reconciliation lane. Recovery receipts are bound to the exact transition/retry generation and fixed work-ledger obligation; they may terminalize/apply/settle existing E work but cannot reserve/fence/create/revise new business truth. Quiescence and abort remain blocked until that lane is closed, its high-water is captured, and every recovery receipt through the mark is terminal.
- Aborted epoch transition attempt: abort is not an escape from a live drain. The current generation may enter `aborted` only after both captured owner admission drains are terminal, the retirement-reconciliation lane is closed and drained, and all capacity-changing settlement obligations for that generation are terminally applied. The `EpochAuthorityTransition` remains the unique lineage for its source pair. An equivalent retry may start only by expected-version CAS on that same record and a fresh retry generation; the immutable admission-closure receipts/high-water marks remain source-boundary evidence because business admission stays closed, while prior-generation drain/reconciliation/settlement/quiescence proof artifacts cannot satisfy the new generation. A contradictory target/digest or second transition row fails closed.
- Reconciliation records evidence and decisions in immutable audit/outbox data. It cannot infer terminal absence from time, request delivery state, or a current read that finds no Assignment.

This is a Saga-style compensating protocol, not a distributed ACID claim. Compensations are explicit domain transitions with evidence; retries, TTLs, present-time absence, transport observations, and a network call made while holding a database row lock are not substitutes for atomicity or terminal-outcome evidence.

## Cutover, protocol quiescence, and rollback

Extraction must not create two Position/capacity writers. A migration snapshot must be linearized after every legacy write admitted before the fence. A later rollback or protocol-authority transition must additionally prove that no nonterminal cross-context state from the retiring epoch can mutate truth after the snapshot.

### Initial legacy-to-Organization cutover

1. Integrate #64 normally so the currently shipped People mutation/concurrency truth is protected.
2. Integrate #96 and then #119 through their canonical Organization stack; descendants adopt protected predecessors with ordinary non-force history.
3. Implement and test the Organization owner and published/versioned capacity contract while this ADR remains Proposed.
4. Enter a durable cutover epoch that rejects new legacy Position/Assignment capacity-mutation admissions. Every mutation admitted before the epoch change must hold a transaction-lifetime admission receipt tied to a pre-existing cutover admission sequence; the barrier atomically closes new admission and captures the sequence high-water mark. It cannot close until each receipt at or below that mark has terminally committed or rolled back. A sleep, request-counter sample, one `pg_stat_activity` observation, or elapsed-time assumption is not drain evidence.
5. Only after that barrier closes, record the authoritative cutover knowledge timestamp/high-water evidence and take the migration snapshot. Project every Assignment fact that is currently recorded-visible at that cutoff across the complete effective-time domain, including wholly past intervals that remain subject to retroactive correction, into the Organization reservation ledger and bind the projection to an immutable manifest/digest. Superseded recorded-history versions remain People/audit provenance and must not be duplicated as simultaneously live reservation debits.
6. The manifest must define a deterministic, versioned mapping from each tenant-qualified legacy `assignment_record_id` in that complete currently authoritative effective-time projection to one opaque migration `assignment_attempt_id`, one reservation identity, and terminal People `committed` evidence rooted in the already-authoritative Assignment. The mapping algorithm/version, exact Assignment effective/recorded evidence, allocation, Position, and normalized `PositionEligibilityCoverage` are manifest inputs; replay of the same snapshot must produce byte-identical identifiers/digests. Existing committed Assignments project as `confirmed`, never as expirable `held` or unresolved `commit_fenced`.
7. Before authority switch, verify tenant, Position, effective interval, allocation, eligibility-coverage union, aggregate sum, deterministic identifier/digest, and terminal-outcome equivalence for the complete projection across past, present, and future effective slices. Any source Assignment that cannot be represented losslessly, any aggregate allocation above `1.0000`, any incomplete staffable Position coverage, or any ambiguous tenant/identity mapping aborts the authority switch. Emit immutable discrepancy evidence; do not drop, clamp, split, round, synthesize, or silently rewrite the legacy fact to make the target ledger pass.
8. Switch Position/capacity write authority to `organization_core`, then switch `people_core` to the published capacity/attempt protocol, then remove the cutover fence. The authority switch establishes the signed owner authority/rollback epoch pair and key-authorization manifest used by the cross-context receipt contract. No legacy transaction admitted before the fence remains able to commit after the projection or authority switch.

### Retiring a live protocol epoch

Rollback, contract-owner migration, or any other change that makes epoch E stale follows one durably arbitrated, two-sided quiescence sequence before E is superseded:

1. Each owner already issues every ordinary E business-mutation admission receipt with the exact source `(authority_epoch=E, rollback_epoch=R)` and a monotonic owner-local `admission_sequence`. Acquire the unique `EpochAuthorityTransition` lineage by compare-and-set against the exact current source pair and bind its immutable intent to the target writer/target epoch pair/transition digest. Initial creation sets retry generation 1 and state `draining`; it does not attempt a distributed transaction across Organization and People. The uniqueness constraint is on the source pair across `draining`, `quiesced`, `aborted`, and `activated`; an `aborted` state never releases it for replacement creation. A concurrent request with the same canonical intent observes the current lineage idempotently; a different target/digest cannot create or repurpose another lineage and must fail closed after refreshing authority.
2. Close Organization E business admission by owner-local expected-gate-version CAS. In the same Organization transaction, reject future E business admissions, capture `organization_admission_high_water`, and publish an authenticated Organization closure receipt bound to transition identity, source `(E,R)`, gate version, captured mark, and `closed_at_retry_generation`. Then perform the equivalent owner-local CAS in People, capturing `people_admission_high_water` and publishing the matching People closure receipt. The order may be reversed. These two closes are intentionally not cross-service atomic: until both closure receipts are durable, the transition remains `draining` and may not freeze recovery work, quiesce, abort, snapshot, or activate. Work admitted by the later-closing owner during the inter-owner gap is covered by that owner's eventual high-water. A request arriving after an owner's local close cannot obtain that owner's E admission sequence. If a later retry generation starts after `aborted`, it references these same immutable closure receipts/high-water marks and does not re-close either gate; their first-close generation is provenance only.
3. Drain Organization and People by their captured local marks. Every ordinary E receipt with `admission_sequence <=` its owner's captured high-water must terminally commit or roll back. Pre-transition or inter-owner-gap transactions do not need and cannot retroactively gain the transition identity; sequence membership is sufficient. The active retry generation produces fresh drain-proof digests from both authoritative owner admission ledgers even when it reuses the same immutable closure receipts/high-water marks. No recovery-work freeze, quiescence manifest, abort, snapshot, or activation begins while either authenticated closure receipt is missing or any captured ordinary receipt remains nonterminal.
4. After both ordinary business-admission drains close, derive a deterministic transition-scoped reconciliation work ledger from authoritative E state. It enumerates every remaining `held`/`commit_fenced` reservation, unresolved attempt, and pending confirm/release/revision/settlement obligation by exact identity/version/digest. Only work-ledger actions may now obtain E recovery admission: safe expiry/release of listed `held`, `terminalize_attempt` for a listed unresolved attempt, or application/settlement of the exact terminal receipt for a listed reservation/Assignment version. Recovery admission is bound to transition identity, retry generation, obligation identity/digest, and monotonic `reconciliation_sequence`; it cannot call `reserve`, `arm_commit_fence`, `create_assignment`, `revise_assignment_capacity`, or an unrelated Position mutation.
5. Execute the reconciliation work ledger until every listed `commit_fenced` attempt has exactly one terminal People `committed` or `aborted` outcome and every terminal E revision/end/confirm/release receipt required for cross-owner equivalence is applied. An obligation may deterministically expose its next exact step—for example, terminalizing an unresolved attempt yields the exact receipt that must be applied—but it cannot introduce a new business-mutation obligation outside the fixed retiring-epoch subject set. New delta fences or successor Assignment versions are prohibited in this lane. Organization confirmed capacity and People authoritative Assignment history must converge to equivalent backing.
6. When the authoritative work ledger is exhausted, atomically close new reconciliation admission and capture `reconciliation_admission_high_water`. Drain every transition/retry-generation recovery receipt with `reconciliation_sequence <= reconciliation_admission_high_water` to terminal commit/rollback, then re-read authoritative E state. Any newly observed unresolved obligation from the fixed retiring-epoch subject set reopens reconciliation within the same generation and repeats the close/high-water/drain cycle; contradictory or newly created business work is a fail-closed invariant violation. The final quiescence manifest records transition identity/version/retry generation, both stable owner closure-receipt identities/digests and local high-water marks, the active generation's freshly computed owner drain-proof digests, the final reconciliation high-water/drain-proof digest, recovery work-ledger digest, terminal outcome IDs/digests, applied reservation versions/dispositions, and proves zero unresolved `commit_fenced` state, zero unapplied capacity-changing terminal outcomes, and no open reconciliation receipt.
7. Only after protocol quiescence is proven may the transition advance from `draining` to `quiesced` by expected-transition-version CAS and bind the immutable quiescence-manifest digest for that retry generation. The rollback/migration high-water snapshot may then be taken. `confirmed` occupancy can be projected because it is bound to terminal Assignment evidence. The target writer projection must be equivalent across the complete effective-time domain required for retroactive correction.
8. Activate the target writer by compare-and-set on the same transition version and exact still-current source `(E,R)` authority pair. The activation transaction atomically records the next authority/rollback epoch pair, marks the transition `activated`, and publishes one immutable activation receipt for the selected target writer. A losing concurrent rollover cannot activate another target: an equivalent replay observes the existing activation; a contradictory target/digest or stale expected pair fails closed and must refresh from current authority. New domain transitions reject E receipts. Historical E receipts remain auditable but cannot regain write authority.
9. If the current retry generation must stop before activation, an operator cancellation request does not bypass drain or settlement. `aborted` is permitted only after both authenticated owner-local closure receipts exist, every ordinary receipt at or below both captured owner high-water marks is terminal, reconciliation admission is closed, every recovery receipt through its captured high-water is terminal, the reconciliation work ledger is exhausted, every capacity-changing E terminal outcome for the generation is applied, `(E,R)` is still current, and no activation receipt exists. The expected-transition-version CAS then marks the same lineage `aborted`; source business admission remains closed and source-pair uniqueness remains owned. The source-boundary closure receipts and captured high-water marks remain immutable lineage evidence because their gates never reopen. Prior-generation drain proofs, reconciliation receipts, discrepancy records, recovery work ledgers, settlement proof, and manifest candidates remain immutable audit evidence but are never accepted as the next generation's proof artifact. An equivalent retry CASes the same transition from `aborted` to `draining`, increments retry generation, keeps both owner-local E business-admission gates closed, reuses the same consistent closure receipts/high-water marks, and freshly recomputes owner drain, reconciliation, settlement, and quiescence proof from authoritative source ledgers/state before a new snapshot. It does not attempt a second gate-close or mint replacement closure receipts. Two concurrent equivalent retries CAS the same expected transition version, so at most one opens the next generation and the loser observes it idempotently. If either stable owner closure receipt is missing or inconsistent with its gate/high-water evidence, either owner still has a captured nonterminal ordinary receipt, any current-generation recovery receipt is nonterminal, any capacity-changing outcome is unapplied, the source pair is no longer current, an activation receipt exists, or target/digest intent differs, abort/retry fails closed rather than creating a second lineage or carrying an unresolved mutation across generations.

A design that intentionally carries unresolved protocol state across an epoch instead of quiescing it must define a versioned successor-epoch re-attestation/handoff manifest that binds each exact reservation, attempt, terminal/nonterminal state, target version/digest, and one successor authority decision without permitting both epochs to authorize writes. This ADR does not select that more complex alternative.

Rollback must be rehearsed before un-fencing. It uses both the local transaction barrier and the protocol-quiescence barrier above, proves projection equivalence at its rollback cutoff, increments the rollback/authority epoch only after the retiring epoch is quiescent, and never re-enables both the legacy People Position/capacity writer and the Organization writer.

## Acceptance before Accepted status

This ADR may move from Proposed only after the owner stack has executable evidence for all of the following on the exact candidate head:

- two concurrent `0.6000` reservations for one Position and overlapping interval: exactly one succeeds;
- two distinct `0.6000` Assignment creates for the same Employment on different Positions: Organization fences may both be valid, but People Employment-root serialization must permit at most one commit and terminally reject/release the loser so visible Employment allocation never becomes `1.2000`;
- non-overlapping future intervals can both succeed when their own Position and Employment slices remain within capacity/allocation;
- exact replay versus same-key/different-digest behavior, plus same-key/different-`assignment_attempt_id` rejection;
- forged signature, wrong issuer/audience, cross-tenant receipt, stale owner epoch, stale rollback epoch, same-`receipt_id`/different-payload replay, mismatched reservation/Assignment target version or digest, and a cryptographically valid receipt signed by a key not authorized for the claimed current epoch/`domain_transition` purpose all fail closed before a cross-context receipt can authorize a write;
- byte-equivalent authenticated receipt replay is idempotent and does not use wall-clock expiry as write authority;
- crash after `held` before commit fence and bounded expiry;
- crash after commit fence before People commit with no release from mere absence;
- a deliberately delayed `create_assignment` racing attempt terminalization: exactly one terminal People outcome (`committed` or `aborted`) wins;
- two distinct correction attempts based on the same prior Assignment version: at most one advances the Assignment root, the stale-predecessor loser is terminally non-committing, and its unused delta fences remain reserved until exact authenticated abort/conflict evidence with target reservation version/digest and `unused_releasable` disposition is applied;
- V1=`1.0000` -> V2=`0.5000` with V2 People-committed but Organization settlement deliberately delayed, followed by a V3=`1.0000` request: V3 cannot be admitted before exact V2 settlement; after settlement it must fence the `0.5000` positive delta, and duplicated/reordered V2 receipts cannot reduce V3 backing;
- a Position close/status-version change racing a fenced create: Organization cannot make the reservation interval ineligible while People can still commit from the authentic fence receipt;
- a reservation spanning multiple contiguous staffable Position versions: canonical eligibility coverage must span the whole interval and an incompatible change to any covered slice must fail closed;

- crash after Assignment commit before confirm with capacity and eligibility remaining fenced;
- a same-Position allocation increase where only the positive delta from the exact settled predecessor backing is pre-fenced and no interleaving exposes allocation above `1.0000`;
- an interval extension where newly occupied slices are pre-fenced before People revision commit;
- a Position move where target occupancy is fenced before People commit and source capacity is not released until target confirmation/revision evidence is durable;
- allocation decrease, interval shortening, and Assignment end where stale/current reads cannot release confirmed capacity and a crash after People commit causes only temporary over-reservation;
- delayed, duplicated, stale, and out-of-order revision receipts bound to exact prior Assignment/reservation versions and fence dispositions, with contradictory evidence failing closed;
- lost/duplicated/out-of-order confirm/release messages with authenticated version/digest-bound idempotency;
- a pre-fence legacy Assignment transaction deliberately held open while cutover starts: projection cannot begin until that transaction commits or rolls back;
- deterministic legacy projection replay with identical migration identities, terminal committed evidence, eligibility-coverage digests, and manifest digest across every currently authoritative past/present/future effective slice;
- a post-cutover retroactive correction or create against a wholly past interval is checked against migrated historical occupancy and cannot make that Position slice exceed `1.0000` or bypass staffable Position coverage;
- deliberately invalid legacy occupancy causing deterministic discrepancy evidence, no authority switch, and no silent normalization;
- an epoch-E Organization reservation/fence transaction and an epoch-E People transaction both admitted before transition creation: one source-pair transition lineage wins, each owner locally closes E admission and captures its own high-water, neither receipt needs retroactive transition binding, and retirement cannot freeze recovery work, abort, snapshot, or activate until both authenticated closure receipts exist and every captured ordinary receipt is terminal;
- an inter-owner admission-close gap: after Organization closes E but before People closes E, a People business mutation may still be admitted; that mutation must fall at or below People’s later captured high-water and drain before recovery freeze/snapshot, while any Organization request arriving after its local close is rejected;
- after ordinary E business admission is closed, a listed unresolved `commit_fenced` attempt can still be terminalized and its exact disposition applied through the transition-scoped reconciliation lane, while new reserve/fence/create/revise/Position business mutations remain rejected;
- retirement reconciliation itself is linearized: closing the recovery lane captures its high-water, quiescence waits for every recovery receipt through that mark to become terminal, the work ledger is exhausted, and no reconciliation transaction can commit after the authoritative snapshot;
- an epoch-E `commit_fenced` attempt deliberately left without terminal People outcome while rollback starts: rollback cannot take its authoritative snapshot or supersede E until both owner ordinary E admissions are fenced/drained, exactly one terminal outcome is established through bounded reconciliation, and its capacity disposition is applied;
- a delayed epoch-E create racing protocol quiescence cannot commit after the captured People business-admission high-water closes; if it was admitted before the People-local close, rollback waits for its transaction and terminal outcome before the snapshot;
- an attempted `aborted` transition CAS while either authenticated owner closure receipt is missing, any captured ordinary owner receipt or recovery receipt remains nonterminal, reconciliation admission is open, or any capacity-changing terminal outcome remains unapplied: abort fails closed and the generation stays draining until those obligations are terminal;
- two concurrent rollover controllers using the same expected `(authority_epoch, rollback_epoch)` pair: one durable transition lineage wins; equivalent duplicate intent observes that transition/activation idempotently, contradictory target intent fails closed, and exactly one target writer becomes active;
- abort after a rollover generation has fully drained and settled but before activation: the source pair remains owned by the same transition lineage, the same immutable source-boundary closure receipts/high-water marks remain valid because source business admission never reopens, prior generation-specific drain/recovery/settlement/quiescence proof remains historical only, and an equivalent retry must create a fresh retry generation on that same transition by expected-version CAS;
- two concurrent equivalent retries of one `aborted` transition: exactly one CAS opens the next retry generation, the loser observes the winner idempotently, neither owner business-admission gate is re-closed, and no second transition row or target writer can appear;
- a retry generation reuses the exact stable Organization/People closure receipts and captured high-water marks but must recompute current owner drain proof from authoritative admission ledgers and must not accept the prior generation's reconciliation/settlement/quiescence proof as current;
- a retry against an `aborted` transition with different target writer/target epoch/digest, stale source pair, existing activation receipt, missing/inconsistent owner closure receipt, or unresolved captured admission/reconciliation/settlement obligation fails closed instead of releasing/reusing source-pair ownership;

- after E is superseded, an otherwise valid E receipt cannot authorize a new domain transition and no E debit/attempt remains orphaned;
- a retired/audit-only signing key that still verifies historical receipts cannot authorize a newly forged current-epoch domain transition even when the cryptographic signature itself verifies;
- migration projection equivalence and rollback rehearsal without a dual-writer interval;
- real two-service/PostgreSQL interleavings proving no effective Position slice exposes allocation above `1.0000`, no Employment portfolio exposes allocation above `1.0000`, no Assignment write is authorized outside fenced Position eligibility, and no cross-service SQL exists;
- connection/resource cleanup and immutable audit/outbox evidence for failures as well as success; and
- buyer-path reserve/fence/create/terminalize/confirm/settle/revise/apply-revision/release plus conflicting Position-change measurements at p95 <= 20 ms under real concurrency without sample shrinking, excluded slow paths, or warm-cache-only evidence.

Synthetic fixtures may prove deterministic mechanism behavior. Buyer-realistic or scientific claims require provenance-backed right-cleared data.

## Consequences

- Position ownership can match the accepted context map without moving worker Assignment history into Organization.
- Capacity and Position eligibility become explicit Organization domain authority rather than implicit People SQL reads.
- Eligibility evidence is a normalized coverage set; no arbitrary single-version shortcut is allowed.
- A post-fence debit cannot be released merely because People currently shows no Assignment; release requires terminal People evidence that also fences a delayed commit for that attempt.
- Confirmed capacity is also evidence-bound after Assignment correction/end. A mutable current read cannot shrink or release it.
- Distinct creates and revisions that affect one Employment cannot over-allocate it merely because they use different Positions, Assignment roots, or attempt IDs: the Employment root and authoritative portfolio re-read form the People-side allocation linearization point.
- Concurrent revisions cannot fork one Assignment lineage merely because they use distinct attempt IDs: existing-Assignment mutations additionally use the stable Assignment root and expected-prior-version CAS.
- A successor capacity-affecting revision waits for authenticated Organization settlement of its exact predecessor, preventing a delayed decrease receipt from under-reserving a later increase.
- Capacity-increasing revisions reserve only their positive Position/time-slice delta from exact settled predecessor backing before People commit; capacity-decreasing revisions release only after terminal People commit evidence. Failures therefore prefer temporary over-reservation to under-reservation or overbooking.
- Cross-Position moves fence and then confirm target capacity before source release, so recovery never depends on a distributed row lock or a check-then-write read.
- Organization cannot independently close or invalidate a fenced effective slice while People can still commit from the authentic receipt.
- Cross-context coordination is deliberately not performed under the Position, Employment, or Assignment root lock.
- Cross-context write-authority receipts survive queues/retries with cryptographic source/integrity proof, explicit issuer/audience/tenant and authority epochs; equivalent replay stays idempotent while forged, retired-epoch, contradictory replay, or a key version not authorized for the claimed epoch/purpose fails closed.
- Initial cutover has an explicit transaction-drain linearization point and a deterministic legacy Assignment-to-confirmed-reservation mapping across the complete currently authoritative effective-time domain, including past slices required for retroactive correction.
- Retiring a live protocol epoch acquires one source-pair transition lineage, then closes Organization and People business admission through separate owner-local CAS/high-water transactions whose authenticated closure receipts form a two-sided barrier. The inter-owner gap is not assumed atomic: work admitted by the later-closing owner is captured and drained. Those source-boundary receipts/high-water marks survive abort/retry because the gates never reopen; only generation-specific drain/reconciliation/settlement/quiescence proof is refreshed. Only after current-generation owner drains does bounded reconciliation run; that recovery lane is separately sequenced and drained before snapshot. Abort is permitted only after both owner closure receipts, ordinary/recovery drains, and settlement complete, and retry advances a fresh proof generation on the same lineage without reopening source business admission.
- Invalid or unrepresentable legacy occupancy is surfaced as immutable migration discrepancy evidence and blocks authority switch.
- Ambiguous post-fence failures fail closed as capacity/eligibility reservation until explicit terminal People evidence exists.
- The protocol adds reservation state, People attempt-outcome fencing, authenticated settlement/revision receipts, Employment-root allocation serialization, Assignment-root CAS, Position eligibility fencing, protocol-quiescence barriers, transition arbitration, bounded retirement reconciliation, key-epoch authorization, reconciliation, and operational evidence that a single local transaction does not require; that cost is accepted only if executable evidence confirms the bounded-context separation remains worthwhile.
- ADR 0004/0005 remain Accepted semantic authority. This ADR amends only the future service-ownership/consistency mechanism after successful extraction evidence.
