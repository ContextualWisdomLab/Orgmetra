# Traceability: Position-capacity source resume after permanent cancellation

## Authority

This document is executable acceptance planning for Proposed ADR 0275, which extends the Proposed ADR 0274 recovery state machine. It is not protected `develop` truth and does not authorize Position ownership extraction.

## Requirement-to-evidence map

| Requirement | RED interleaving | GREEN acceptance |
| --- | --- | --- |
| Never reopen the retired source pair | Begin with `(E,R)` Organization/People gates closed and a fully drained `aborted` rollover. Attempt a new business mutation using `(E,R)` during and after permanent cancellation. | Every new `(E,R)` admission fails. The only admissible resumed business authority is the fresh pair `(E,R+1)` after terminal source resume. |
| Linearize cancellation before owner adoption | Start retry and permanent-cancel controllers from the same `aborted` transition version. Delay both transition CAS attempts and attempt owner-local `(E,R+1)` adoption before either CAS has won. | No owner can adopt before a single expected-version CAS moves the lineage to `source_resuming`. If retry wins `aborted -> draining`, fresh-pair adoption count is zero. If cancellation wins `aborted -> source_resuming`, retry and target activation fail closed. |
| Govern the cancellation decision | Present a cancellation decision with stale policy/evidence version, wrong purpose, wrong transition/source pair, mismatched digest, or an actor not authorized for that purpose. | The transition remains `aborted`; no `source_resuming` intent or owner adoption receipt is created. The accepted decision is purpose-bound and digest-bound to the exact transition and fresh-pair intent. |
| Two-sided fresh source adoption | After the lineage is `source_resuming`, commit Organization adoption of `(E,R+1)` while People has not adopted it, then attempt Position/Assignment business mutations. | Both business lanes remain closed. No HR business mutation is admitted until both authenticated adoption receipts and the transition-level resume receipt are durable. |
| Roll forward after partial adoption | Enter `source_resuming`, commit one owner's `(E,R+1)` adoption, then attempt retry, target activation, return to `aborted`/`draining`, or reversion of the adopted owner to `(E,R)`. | Every contradictory operation fails. Recovery can only complete the same source-resume intent by adopting the missing owner, recording `source_resumed`, and opening the already-installed fresh-pair gates after terminal receipt verification. |
| Authenticate terminal gate authority | After both owner adoption receipts are valid, present a forged/unsigned or wrong-audience `SourceAuthorityResumeReceipt`, then separately complete a valid resume, start a later transition that closes `(E,R+1)` with a newer gate version, and replay the old valid resume receipt. | Forged, stale-transition, wrong-pair, wrong-audience, wrong-purpose, audit-only-key, or mismatched-digest resume receipts fail before gate mutation. A genuine gate-open CAS is pinned to the adoption-installed expected gate version and exact resume-receipt identity/digest; once a later transition advances/closes the gate, replay cannot refresh that expected version or reopen it. |
| No source-pair ABA | Retain the old `(E,R)` closure receipt/high-water and attempt to use it as closure proof for a later migration starting from `(E,R+1)`. | Verification rejects the old receipt as source-boundary proof for the new lineage. It remains queryable only as immutable audit evidence. |
| One terminal path per lineage | Race an equivalent `aborted -> draining` retry controller against the permanent-cancel controller's `aborted -> source_resuming` CAS using the same expected transition version. | Exactly one expected-version CAS wins. The loser refreshes and fails closed or follows the winner. A lineage never has both target activation and `source_resumed`, and owner adoption cannot precede the cancellation winner. |
| No target activation after permanent cancel | Win `source_resuming`, complete both source adoption receipts and source resume, then replay a previously valid target activation command/receipt. | Activation is rejected from `source_resuming` onward; after `source_resumed` it remains permanently rejected. Target activation count remains zero. |
| Crash-safe pre-adoption intent | Crash after the `source_resuming` transition CAS but before either owner adopts `(E,R+1)`. | Recovery replays the exact immutable source-resume intent and continues owner adoption. It neither creates a second intent nor falls back to `aborted -> draining` because adoption receipts are still absent. |
| Crash-safe partial adoption | Crash after Organization has durably adopted `(E,R+1)` but before People adoption. | Organization does not reopen business admission. Replaying Organization adoption is idempotent; after People adopts the exact same pair/intent, the transition completes source resume without a second lineage or cross-service transaction. |
| Crash-safe finalization | Crash after both adoption receipts are durable but before `SourceAuthorityResumeReceipt`, then separately crash after terminal resume before one owner observes it. | First recovery verifies the two receipts and completes the same `source_resuming -> source_resumed` CAS. Second recovery opens only the already-installed `(E,R+1)` gate after verifying the signed immutable terminal resume receipt and the adoption-installed expected gate version. |
| No successor transition from partial resume | After one or both owners have installed `(E,R+1)` but before terminal `source_resumed` and both fresh-pair gates are open, attempt to create a new `EpochAuthorityTransition` sourced from `(E,R+1)`. | Creation fails closed. Only terminal `source_resumed` plus both source-owner gates reporting open `(E,R+1)` permits a later transition, which must capture fresh `(E,R+1)` closure receipts/high-water marks. |
| Receipt integrity and purpose | Replay adoption/resume receipts with changed source writer, old/new pair, transition version/state, source-resume intent, cancellation decision, tenant/audience, payload digest, or a valid historical key that is `audit_only` for `(E,R+1)`. | Every mismatch fails before domain mutation. Only byte-equivalent replay under a verification key authorized for the claimed pair and `domain_transition` purpose is idempotent. |
| Preserve HR domain truth | Start from settled Position backing and authoritative Assignment history, permanently cancel the rollout, resume the same source writer, and compare domain facts before/after. | Employment/Assignment/Position truth and effective occupancy are byte-/semantically equivalent apart from authority-control metadata and audit receipts. Source resume does not synthesize, rewrite, drop, clamp, or duplicate HR facts. |
| Restore availability without dual writer | Hold the target unactivated, complete source resume, and issue a normal HR mutation through the source writer. | Mutation succeeds only at `(E,R+1)` after `source_resumed` and fresh-pair gate opening. There is no interval where the abandoned target and resumed source both possess write authority. |

## PostgreSQL concurrency fixture

The executable fixture uses separate Organization and People PostgreSQL connections plus an independent transition coordinator connection. Owner-local gate/adoption changes commit in separate database transactions. Tests must not replace this with one transaction spanning both owner schemas or a test-only cross-service SQL shortcut.

The fixture starts from an exact authoritative source pair `(E,R)`, a single `EpochAuthorityTransition`, durable Organization/People closure receipts and captured high-water marks, terminal ordinary drains, a closed/drained reconciliation lane, zero unresolved `commit_fenced` obligations, equivalent Organization backing/People Assignment history, and no target activation receipt.

For the retry-versus-cancel race, both controllers read the same `aborted` transition version. A synchronization barrier releases the transition CAS attempts concurrently: retry attempts `aborted -> draining`, while cancellation attempts `aborted -> source_resuming` with an immutable cancellation/source-resume intent. Owner-local adoption calls are blocked behind a verified winning `source_resuming` state and intent digest. Assertions require one state-path winner; if retry wins, adoption count is exactly zero, and if cancellation wins, retry generation does not advance and target activation remains rejected.

For pre-adoption crash recovery, stop the coordinator immediately after the `source_resuming` CAS and before either owner-local transaction begins. Restart from durable state and assert that the same source-resume intent, fresh pair, cancellation decision digest, and transition version are replayed. A replacement intent or retry path is contradictory evidence.

For partial adoption, pause People before its owner-local adoption commit. Organization may persist its authenticated adoption receipt, but a concurrent business-admission request on either owner must remain blocked. While paused, attempt retry, target activation, state reversion, old-pair gate reopening, and successor `(E,R+1)` transition creation; all must fail. Release People, verify the exact same fresh pair/source writer/source-resume intent, then finalize one immutable resume receipt before admitting business work.

For terminal-resume receipt authority, first keep the transition in `source_resuming` with both authentic adoption receipts durable and inject forged, unsigned, wrong-audience, stale-version, wrong-pair, and historical-`audit_only`-key variants of `SourceAuthorityResumeReceipt`; neither owner gate may change. Then finalize one correctly signed receipt, open both gates with CAS values pinned to their adoption-installed gate versions, and start a later transition that closes `(E,R+1)` and advances those gate versions. Replaying the old valid resume receipt after that closure must fail rather than re-reading the new version and reopening either gate. The fixture records the resume receipt ID/digest and expected gate version used by each successful open so stale capability replay is observable.

For successor-transition admission, complete `source_resumed` but hold one owner's fresh-pair gate-opening transaction. A new transition sourced from `(E,R+1)` must still fail. After both gates durably report open `(E,R+1)`, a later transition may begin only with new owner-local closure receipts/high-water marks for that fresh pair.

## Negative evidence

These observations are never sufficient to authorize source resume: elapsed time, absence of active database sessions, an empty queue sample, a current read that finds no Assignment, provider/gateway success, one owner's adoption receipt, an old quiescence manifest from another retry generation, an operator's free-form cancellation assertion, an authenticated actor without a current purpose-bound cancellation decision tied to the exact transition, or possession of an old terminal resume receipt without its adoption-installed expected gate version.

Administrator bypass, direct gate mutation, force-push, destructive rebase, a second transition row for `(E,R)`, adoption before `source_resuming`, and successor-transition creation from a partially resumed `(E,R+1)` pair are not test shortcuts. Tests must exercise the same fail-closed state machine intended for production.

## Performance and operability acceptance

Where authority validation is on an interactive Position/Assignment mutation path, measure real concurrent requests against the buyer-path p95 <=20 ms target. Report query, lock-wait, receipt-verification, connection-pool, and application-runtime components separately when the target is missed. Do not reduce contention samples, exclude slow failed-closed requests, or pre-warm an unrealistic cache to make the threshold pass.

Operational evidence must expose: source pair, transition identity/version/state including `source_resuming`/`source_resumed`, retry generation, both closure receipt digests/high-water marks, cancellation decision identity/digest and policy/evidence version, immutable source-resume intent digest, both fresh adoption receipt IDs/digests, signed terminal resume receipt ID/digest/key version/purpose, target activation receipt absence, gate state/pair plus adoption-installed/open-CAS version for each owner, and the current `domain_transition` signing-key authorization. PII beyond tenant-qualified opaque domain identifiers and the minimum accountable-actor evidence required by policy is not required for this control-plane evidence.

## Release gate

ADR 0274 and ADR 0275 remain Proposed until these interleavings are executable on the canonical owner stack after prerequisite protected integration. Documentation review or synthetic state-machine examples alone are not distributed-correctness evidence. The implementation owner must preserve the same invariants through code, schema, API/receipt contract, security tests, recovery rehearsal, and normal protected-branch review/merge governance.
