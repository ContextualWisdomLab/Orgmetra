# Purpose-bound access to HR personal data

## Customer action

Before enabling this persistence profile, the customer must map every calling
role to an allowed HR purpose, resource scope, retention period and reviewable
approval path. A database connection alone is never authorization.

## Why Orgmetra does not blanket-mask PII

Authorized HR users need names, employment facts and related evidence to perform
recruiting, onboarding, workforce administration, employee support and legally
required recordkeeping. Replacing the system-of-record values with irreversible
masks would break those workflows and could create new identity errors.

Orgmetra instead applies layered controls:

1. the host authenticates the actor;
2. policy evaluates tenant, role, purpose, resource and decision context;
3. the repository binds the authorized tenant to one transaction;
4. forced PostgreSQL row-level security independently scopes rows;
5. relationship constraints reject cross-tenant references;
6. authoritative mutations append reference-only audit evidence atomically;
7. exports, retention and deletion follow separate approved workflows.

## Data classification

| Data family | Example | Default classification | Handling |
| --- | --- | --- | --- |
| Person identity | display name, legal identity reference | restricted HR | encrypted storage, purpose-bound read, access audit |
| Employment fact | status, effective period, assignment | restricted HR | bitemporal history, least privilege, controlled export |
| Candidate evidence | application and evidence references | restricted recruitment | recruiter scope, retention schedule, decision provenance |
| Assessment response | raw item or narrative response | highly restricted assessment | owned by Psychometrics Commons; not copied into generic audit |
| Compensation | amount and currency | highly restricted compensation | separate role and export policy |
| Audit metadata | actor, purpose, action, resource reference | confidential control evidence | append-only, no HR content, longer integrity retention |

## Trust boundaries

- `PurposeContext` is accepted only from an authenticated service boundary.
- Request headers, browser fields, model output and event payloads cannot select
  a tenant directly.
- A custom PostgreSQL setting is not a credential. Generic SQL access would let
  a caller set arbitrary session state and is prohibited for application roles.
- Application roles must be non-owner, `NOSUPERUSER` and `NOBYPASSRLS`.
- Service-to-service calls carry opaque references; they do not broadcast names,
  resumes, assessment responses or compensation values on the event bus.

## Control evidence

| Control objective | Evidence generated by this slice |
| --- | --- |
| Logical tenant isolation | forced-RLS migration and cross-tenant tests |
| Least privilege | application-role fixture and minimal workflow permissions |
| Purpose limitation | immutable `PurposeContext` and audit `purpose_code` |
| Auditability | same-transaction `audit_event` append |
| Data minimization | reference-only audit schema contract |
| Change integrity | append-only triggers for high-impact facts |
| Secure development | immutable action pins, exact coverage and docstring gates |

This mapping supports CSAP- and SOC 2-oriented engineering evidence. It does not
claim that a deployment or organization is certified.

## Required deployment work

- enterprise identity and policy integration, preferably through Keyverse;
- managed secret storage and rotation;
- encryption and customer-managed-key options;
- privileged-access review and break-glass procedure;
- backup, restore, PITR and deletion/retention rehearsal;
- export approval and watermarking where required;
- regional residency and subprocessors documentation;
- incident-response playbook and independent penetration testing.
